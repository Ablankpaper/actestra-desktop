# P8.4 Internal-Beta Acceptance Runbook

Status: implementation contract only. No target is accepted by this document.

This runbook defines how an operator produces clean-machine evidence for the
exact P8.3 candidate. It does not permit a builder package, a local profile,
synthetic-provider run, or an `unsupported-platform` result to be reported as
internal acceptance.

## Required binding

Every record must name the exact candidate manifest SHA-256, candidate version,
source commit, CI run, target ID, architecture, and clean-machine acceptance
environment. The three target records must use one candidate manifest digest and
one source commit. Evidence is metadata-only and must not include credentials,
prompts, completions, patch text, workspace paths, profile paths, or user data.

Accepted targets are:

| Target | Acceptance environment | Package |
| --- | --- | --- |
| `macos-15-arm64` | macOS 15 arm64 | DMG and ZIP |
| `windows-11-x64` | Windows 11 24H2 x64 | NSIS EXE |
| `ubuntu-24.04-x64` | Ubuntu 24.04 LTS x64 | DEB |

The CI builder identity is not the clean-machine identity. A GitHub-hosted
runner is not evidence that the corresponding clean-machine journey occurred.

## Operator sequence per target

1. Provision a machine matching the accepted environment with no prior Actestra
   profile or installation. Record only the OS and version, architecture, and
   target ID.
2. Verify the candidate manifest digest and package digest before installation.
   Refuse a mismatch; do not retry with a different artifact.
3. Install the exact package. Record installer acceptance, installed version,
   fresh-profile creation, launch, and cleanup.
4. Run the existing General, Goose, Team, approval, restart, privacy, and
   cancellation journeys from the installed app. The P8.4 record references
   bounded evidence digests; it does not copy their content.
5. Install the accepted predecessor, create a durable Artifact, upgrade to the
   candidate, restart, and verify the Artifact and state schema remain visible.
6. Inject the documented update failure, confirm partial update rejection,
   restore the previous version, retain state, and require explicit operator
   confirmation before another update attempt.
7. Uninstall the application. Exercise both data choices separately: retain
   user data and remove user data. Prove application removal, data-choice
   presentation, no residual process, and cleanup.
8. Configure a real third-party Provider on the clean machine. Credentials are
   entered interactively by the operator and never copied into CI, logs,
   evidence, issues, or this repository. Verify message round-trip, Artifact
   result, restart recovery, and credential redaction.
9. Open a sanitized issue in the repository issue-intake channel if a journey
   fails. Include candidate digest, target, OS version, journey ID, and closed
   failure code only.

## Evidence creation and checking

The machine-readable record is checked with:

```bash
bun run p8:clean-machine:check -- \
  p8-clean-machine-macos-15-arm64.json \
  p8-clean-machine-windows-11-x64.json \
  p8-clean-machine-ubuntu-24.04-x64.json
```

The checker requires all five P8.4 journeys on every target, a real-provider
mode for the Provider journey, a clean-machine flag, an exact candidate binding,
redacted runbook and issue-intake revisions, and all journey checks set to
`true`. Missing, synthetic, mismatched, leaked, or oversized evidence fails
closed.

## Current limitations

This checkout can run macOS diagnostics only. Windows 11 and Ubuntu 24.04
clean-machine evidence requires the corresponding machines or an independently
controlled acceptance service. Formal signing/notarization and a real-provider
run require operator-owned external credentials and are intentionally not
performed by CI. Until those external records exist and pass the checker,
P8.4 remains `evidence-incomplete`; no release, distribution, or user-
acceptance claim is authorized.
